# Lumen — Agentic Data Intelligence Platform: Architecture Review

## A. Critical Weaknesses

1. **Static Orchestration Disguised as Agentic**: The pipeline claims to be "agentic," but the `OrchestratorAgent` largely relies on rigid, static plans (`upload`, `process`, `full`). The `dynamic` planning fallback uses a rudimentary LLM call, but there's no true reactive planning, condition-based branching (e.g., skip feature engineering if dataset is small/clean), or robust failure handling.
2. **Brittle Code Execution (`QueryAgent`)**: The natural-language-to-Pandas engine is a single-shot execution. If the LLM generates syntax errors or references a nonexistent column, it fails instantly with an unhelpful fallback message. There is no multi-pass reasoning (generate $\to$ execute $\to$ refine).
3. **No Short-Term or Contextual Memory**: The `QueryAgent` is completely stateless between queries. It hashes `dataset_id` + `question` for caching but cannot handle follow-up questions (e.g., "Now group that by region").
4. **Poor Context Compression**: Datasets are injected into prompts via naive truncation (e.g., `_trim` logic in `templates.py`). For wide datasets, critical column metadata or statistical context is silently dropped, leading to hallucination.
5. **No Query Understanding Layer**: The user query is passed almost raw to the LLM. There is no preliminary step to classify intent (e.g., general vs. time-series), disambiguate entities, or map natural language terms to actual column names before generating code.

## B. Missing Components Limiting Performance

1. **Reflection / Critic Agent**: While an `EvaluatorAgent` exists, it evaluates the final report statically. There is no continuous loop where a Critic Agent evaluates *intermediate* steps (e.g., evaluating the chart configuration generated by the `VisualizationAgent`).
2. **Vector-Backed Semantic Search for Schema**: Relying on raw schema injection will break for tables with hundreds of columns. A tool selector or schema-retriever (semantic search over column names/descriptions) is missing.
3. **Guardrails & Confidence Scoring**: Insights and generated code do not output calibrated confidence scores, and there's no programmatic guardrail layer to flag potentially misleading business insights before displaying them.
4. **Agent State/Memory Management**: The orchestration relies entirely on cache TTLs. A robust persistence mechanism for agent graphs (e.g., LangGraph state or Checkpoint saving) is needed to handle long-running analytical processes and human-in-the-loop interactions.

## C. High-Impact Improvements (Ranked by Priority)

1. **Self-Healing Code Execution (Multi-Pass Query)**: Update the `QueryAgent` to catch Pandas execution errors, feed the stack trace back to the LLM, and attempt a fix. This immediately drastically improves user trust.
2. **Query Understanding Router**: Add an intent-classification layer before `QueryAgent` to determine if a query requires simple aggregations, complex ML inference, or just retrieving a cached insight.
3. **DAG-Based Dynamic Orchestration**: Replace static plan arrays with a true graph structure where agents are nodes, and edges dictate conditional execution (e.g., `FeatureAgent` only runs if `UnderstandingAgent` flags high-cardinality categoricals).
4. **Semantic Caching & Session Memory**: Introduce conversational memory (e.g., last 5 user queries and their code ASTs) to support multi-turn data exploration.
5. **Structured Output Enforcement (Instructor/Pydantic)**: Move away from fragile string extraction and preambles (`extract_json_with_preamble`). Enforce strict JSON schema validation at the LLM provider level using tool calling or structured outputs.

## D. Future Enhancement Roadmap (Step-by-Step)

### Phase 1: Robust Execution & Memory
- **Week 1-2**: Implement Multi-pass code execution in `QueryAgent`. Enforce LLM Structured Outputs (JSON Schema) across all agents to eliminate JSON parsing errors.
- **Week 3-4**: Implement Thread/Session memory in cache. Allow users to ask follow-up questions referencing previous `result_df` outputs.

### Phase 2: True Agentic Orchestration
- **Week 5-6**: Refactor `OrchestratorAgent` into a Stateful Graph (e.g., using LangGraph concepts). Implement condition edges (skip `FeatureAgent` if data is clean).
- **Week 7-8**: Add a Semantic Router. Route analytical questions to `QueryAgent` and high-level questions to `InsightAgent` without running the whole pipeline.

### Phase 3: Scale & Trust
- **Week 9-10**: Build a RAG system for wide-table schemas. Instead of dumping 500 columns into the prompt, retrieve only top-K relevant columns based on the query.
- **Week 11-12**: Implement Explainable AI (XAI) outputs. Return confidence intervals alongside point metrics in insights and charts.

## E. Architectural Upgrades for Production-Grade Systems

1. **LLM Gateway / Proxy Layer**: Move from LiteLLM straight calls to a dedicated proxy (e.g., LiteLLM Proxy Server or Portkey) to handle robust load-balancing, token-based rate-limiting, and cost tracking per user session.
2. **Asynchronous Task Queue (Celery/Temporal)**: Python `asyncio` inside FastAPI is not sufficient for production data pipelines. Use Temporal or Celery to manage long-running ingestion and ML tasks, allowing the API to return 202 Accepted and stream progress.
3. **Agent State Store**: Use a dedicated Graph Database or Postgres JSONB state table to store agent thread history, allowing resuming of paused DAGs (Human-in-the-loop approval for generated reports).
4. **Secure Code Sandboxing**: `multiprocessing` with AST validation is inherently vulnerable to sandbox escapes. Replace `_secure_runner` with an isolated WASM sandbox (e.g., Pyodide) or Firecracker microVMs for absolute tenant isolation when running generated Pandas code.
